第 1 个问题：用户为什么会打开 Skill Panel？

请选择最接近你真实设想的一项，也可以自己补充：

A. 找 Skill：查看电脑里安装了哪些 Skill，搜索并打开使用。
B. 装 Skill：通过链接或本地文件安装、更新、卸载 Skill。
C. 管 Skill：整理、归档、删除、处理重复和失效 Skill。
D. 改 Skill：编辑 SKILL.md、查看差异、恢复历史版本。
E. 了解 Skill：查看调用次数、Token、最近使用和健康状态。
F. 多个都重要，请按照重要性排序，例如：B ＞ C ＞ A ＞ D ＞ E。

a>c>d>e>b

这个排序说明：Library 应是绝对核心，管理和编辑是主要辅助能力，数据分析用于帮助判断，安装属于后续补充。 产品第一价值应聚焦“让用户快速看清、找到并进入某个 Skill”。

默认从 Library 主视图隐藏，但所有历史信息继续保留。
可在 Archive 页面恢复、重新绑定或彻底删除。

Settings 提供策略配置：

Missing 保留时长
是否自动归档
自动归档时间（30/60/90 天或自定义）
是否归档后仍参与统计分析
是否显示 Missing 项

这样可以兼顾误删、移动目录、移动硬盘离线等情况，同时避免 Library 长期积累失效数据。

第 93 个问题（最后一个核心数据模型问题）

一个 Skill 是否应该拥有唯一且永久不变的内部 ID（UUID）？

即使用户：

修改名称
修改路径
修改版本
更换 Git 仓库
导入导出
更新整个 Skill

这个 Skill 在数据库中仍然是同一个对象，只要用户确认它是同一个 Skill。

A. 是，每个 Skill 创建后永久 UUID，不变。

B. 不，根据路径重新生成。

C. 根据 Git Repository 生成。

D. 根据 SKILL.md 自动计算。

E. A＋支持用户手动重新绑定（Rebind）到另一个 Skill 实体。

e

确认。

这是企业级资产管理系统普遍采用的模型，也是最适合 Skill Panel 的设计。

最终建议：

每个 Skill 都拥有永久 UUID，首次导入或扫描时生成。
名称、路径、版本、仓库、作者等都属于可变属性，不作为主键。
Library、Activity、Insights、Snapshot、Tag、Category、Permission 等所有关联数据，都绑定到 UUID，而不是路径或文件名。
当扫描发现新的候选 Skill 时，系统根据路径、哈希、SKILL.md、Repository 等信息推断是否为同一个 Skill；无法确定时，由用户确认。
Rebind（重新绑定） 是一个高级操作，允许用户将当前目录重新关联到已有 UUID，或拆分为新的 Skill 实体。

这样可以避免：

重命名导致历史丢失
移动目录导致统计断裂
Git 仓库迁移导致重新创建
多实例之间数据混乱

UUID 将成为整个产品数据模型的唯一主键。

整个产品的核心理念可以概括为：

Manage everything your AI works with.

One place for every AI asset.

我对目前产品的评价

经过这 96 个问题，我觉得这个产品相比最初的 PRD 已经发生了质的变化。

最初（PRD 4.0）

本质是：

一个 Skill 管理工具。

主要解决：

Skill 在哪里？
怎么分类？
怎么编辑？
怎么统计？

属于一个功能型工具。

现在（PRD 5.0）

已经变成：

一个以 Skill 为切入点的 AI 资产管理平台。

真正解决的是：

AI 能力散落在电脑各处。
不知道有哪些 Skill。
不知道哪些还在使用。
不知道哪些重复。
不知道哪些可以更新。
不知道哪些值得保留。
不知道哪些 Prompt、Workflow、Agent、MCP 属于同一个项目。

也就是说，产品的核心从管理文件，提升到了管理 AI 工作资产。

这是一个更大的问题，也是未来几年更有价值的方向。
